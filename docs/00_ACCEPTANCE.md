# 验收关卡：不能越级宣布完成

## G0：工程闭环

检查 pytest 原始输出；测试覆盖参考规则、公开信息隔离、采样、动作 mask、网络梯度、并行采集、数据 split、checkpoint 恢复、控制桥拒绝未知状态。`scripts/smoke.py` 必须实际完成收集→训练→重新加载→评测。报告中始终保留 backend。

交付时此关已在 CPU 完成；精确结果见该轮的全量测试记录（近期为 `reports/s2_junit.xml` 与 `reports/s1r_junit.xml`）。native 模块 skip 不是通过。这个关卡只证明代码在已测范围可执行，不证明游戏规则正确或策略强。

## G1：目标 5070 机器

`doctor --require-cuda` 退出码 0；记录 GPU／显存／驱动／PyTorch wheel。实际网络 CUDA 前向／反向均成功，梯度有限。用选定模型／微批次跑至少 10 次优化步并记录峰值，保留操作系统／依赖锁定信息。BF16 只在设备支持时启用；否则 FP32。不得静默 CPU 回退。

参数目标为一个启动建议：不超过可用显存预算，留给显示／其他进程余量；不能假定 doctor 的微型模型测试自动证明正式微批次一定放得下。

## G2：原版模拟器 pilot

完整上游 SHA 已锁定；native 实际可导入，不能只看编译日志。所有 native 测试实际执行；额外进行至少 1,000 个限定场景／动作序列的随机回放，记录 0 非法动作、0 崩溃、0 未解释的 undefined behavior 标记。每种卡和升级至少有定向测试；每种敌人至少覆盖全部可见行为分支。

1,000 是工程压力测试目标，不是“规则已百分百正确”的统计证明。对回放中超步数的战斗单独分类，不能删掉。搜索采样必须保持公开根状态不变，且不能修改真实环境。

## G3：原游戏一致性与公平性

必须有独立于本模拟器生成的原游戏轨迹。先为无随机分支动作构造单步测试，再针对相同初始状态、相同已控制随机结果／或同种子已校准 RNG 消耗的序列做逐步比较。随机结果不一致时区分“规则错误”和“RNG 后验／耦合不同”，不得靠放宽所有字段解决。

要求给出：游戏版本、Mod 版本、引擎 commit、场景注入方式、动作脚本、原始轨迹、规范化映射、差异报告、每种覆盖的证据。初始目标 100 条短规则轨迹 + 100 场完整 pilot 战斗；这是最低实施目标，并非穷举证明。

当前 native 是独立未来 RNG 近似，不是原版相关随机流的精确后验。即便 pilot 差分通过，这一限制也必须留在报告。读到任何不应可见的保存字段都要截断接口，不要在网络里“希望它不用”。

## G4：战斗能力进步

冻结评测场景分布和算力预算，在开发 val 上比较启发式、无网络搜索、纯网络、网络辅助搜索。第一轮小样本只 smoke；晋级使用至少 1,000 个固定验证场景的独立整场结果，按场景配对计算效用差和胜负差的置信区间。

强度晋级不能只看训练 loss 或对教师的 top-1 agreement。要求零非法动作／崩溃、截断全部明确、死亡率没有不允许的退化、存活 HP／效用确有提升、决策延迟在声明预算内。多次看验证结果会过拟合；最终只在模型选定后生成新测试 manifest。

`evaluate` 提供 Wilson 区间、效用差 bootstrap 和截断上下界，**没有自动给出晋级结论**。对模型 A→B 晋级，要显式将 A、B 的独立报告按相同场景 ID 配对；不同预算比较须同时列出耗时。配对初始种子不保证两策略未来随机路径完全相同。

## G5：用户最终阶段目标

铁甲战士完整战斗接口：所有常规卡和生成卡、升级／变费／X 费、选择和多选、药水、遗物／状态计数、多敌人／死亡复活、精英／Boss／Heart、实际游戏从任意支持战斗状态接入。每项有 capability matrix 和原版测试，而不是仅扩充名字枚举。

进一步谈“超过人类”必须指定合法观察、战斗分布、起始卡组／HP／药水、可用思考预算、指标及人类基准；局内夹具强度不能直接推断 A20H 整局胜率。
